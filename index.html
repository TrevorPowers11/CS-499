Professional Self-Assessment

As I complete my Bachelor of Science in Computer Science at Southern New Hampshire University, I am interested in work that combines software development, information technology, and security. My coursework and capstone have helped me become more systematic about solving problems. I now look beyond whether a program runs and consider whether its behavior is understandable, its data is handled carefully, and its limitations are documented. This portfolio presents that growth through an Android inventory application and two enhancements to an animal shelter dashboard.

Growth across the program

My CS 465 full stack coursework gave me experience beyond the artifacts in this portfolio. I worked with an Express application, separated API controllers, models, and routes, and connected MongoDB through Mongoose. Testing the trip endpoints gave me specific evidence of behavior: the collection and a valid trip request returned HTTP 200, while an unknown trip returned HTTP 404 with a clear message. Resolving routing, dependency, and model-registration problems helped me learn to trace a failure through the application rather than change unrelated code.

This experience strengthened my interest in maintainable systems. I value clear boundaries between responsibilities, repeatable setup steps, and honest reporting of what has been tested. A result from a small local test is useful evidence, but it does not prove that an entire application is ready for deployment.

Collaboration and communication

My IT program experience at Kettering City Schools included computer imaging, hardware repair, software installation, and end-user troubleshooting. Those tasks connected technical work with the needs of the person using the computer. My freight work has also involved teamwork, inventory accuracy, and shared deadlines. These experiences reinforce the importance of making a problem understandable, clarifying responsibilities, and communicating progress.

In the capstone, the code review provides a way to explain existing behavior and proposed changes to a technical audience. The narratives explain the reasons behind those changes, while the portfolio gives a reader a way to compare original and enhanced work. My instructor feedback on CS 340 showed that readable code is only part of a useful handoff: another developer also needs clear feature descriptions and setup instructions. For collaboration, I would use reproducible issue descriptions, focused reviews, and documented decisions so teammates can evaluate a change without guessing its purpose.

Algorithms engineering and security

Data structures and algorithms have helped me evaluate the cost of a design. A dictionary index can narrow an exact search, but it also requires memory and must be refreshed when its source data changes. Database indexing and pagination address a different part of the system. Choosing between these approaches requires attention to the workload and the freshness of the data, rather than assuming one approach is always faster.

My security mindset has also developed through reviewing input validation, credentials, and failure behavior. The inventory enhancement replaces plaintext password storage with hashing, but its unsalted SHA-256 implementation is still a limitation. Recognizing that limitation matters as much as describing the improvement. The database enhancement adds controlled queries, validation, environment-based connection configuration, and safer errors. These choices reflect my goal of anticipating misuse and reducing unnecessary exposure of data.

How the portfolio fits together

The software engineering artifact shows changes to validation, account handling, and database feedback in the inventory app. The algorithms enhancement adds AnimalIndex to the shelter dashboard, with breed and ID lookup structures and sorting. Five focused checks during final preparation passed for duplicate IDs, combined conditions, rescue filtering, descending numeric sorting, and unmatched searches. The separate database enhancement demonstrates MongoDB pagination, aggregation, indexes, and validation. Together, these artifacts connect interface behavior, computation, and persistent data.

The portfolio supports the five program outcomes through review and collaboration practices, written and oral communication, algorithmic trade-offs, practical implementation, and security analysis. It also identifies remaining work, including Android runtime verification and broader live database testing. I want to bring this combination of practical troubleshooting, careful evaluation, and willingness to improve into an entry-level technology role.

Artifact and purpose

I selected the inventory application I created in CS 360 in 2026. The Android app uses Java and SQLite to support account creation, login, inventory updates, and optional low-stock text alerts. I chose it because inventory work is familiar to me, and the project shows how software can support a practical task. My CS 499 enhancement focuses on validating input, handling database results, and improving account handling.

Changes and skills demonstrated

The original app stored passwords directly. The enhanced DatabaseHelper hashes passwords with SHA-256 before storing or comparing them. Account creation also checks password length and character requirements, then asks the user to log in. These changes demonstrate attention to sensitive data, although this implementation still has limits: the hash is unsalted, and the submitted change does not include a migration for existing plaintext passwords.

I added checks for item names longer than 50 characters, invalid integer quantities, and negative quantities. Catching NumberFormatException prevents malformed quantity input from following the normal save path. Database insert, update, and delete methods now return success indicators. The interface can use those results to distinguish successful operations from failures instead of always reporting success. These changes connect validation, persistence, and user feedback more clearly.

Learning and feedback

This work helped me understand that a feature is not finished just because it works with expected input. The application also needs to respond clearly when data is invalid or an operation fails. Changing database methods to return results required the calling code to use those results consistently. I also learned to distinguish removing plaintext password storage from completing a robust authentication design.

My CS 360 instructor described the original code as clean, organized, and functional, while noting that the main screen was busy. This enhancement improves reliability and feedback, but the two main layout files remain unchanged. Simplifying the screen remains an improvement to address; I do not count it as completed. The original and enhanced source files were compared during final portfolio preparation. Android emulator testing of this submitted version still needs to be documented.

The remaining authentication limitations show why security requires continued review. The narrative and code review contribute to Outcome 2 by explaining decisions and limitations. Artifact and origin

I chose the Grazioso Salvare Animal Shelter Dashboard project that I designed in CS 340 Client Server Development class back in 2026. This Python notebook makes use of MongoDB CRUD functions to fetch records from the Austin Animal Center and presents them in a Dash table, graph, and map. Users have an option to select the rescue as water, mountain, or disaster. In the original code, there is a callback that queries the database based on the user choice.

Why this artifact belongs in my ePortfolio

In this case, the dashboard represents an algorithmic decision made by the user on which animals meet the set conditions and what is the correct order of their appearance. To achieve this, I have extended the functionality of the dashboard with the creation of the class AnimalIndex, containing a snapshot of records and creation of dictionaries based on breed and animal ID with their corresponding positions. The exact search can extract possible positions out of the hash buckets, and several indexed conditions are first intersected while other rescue criteria are checked later. The sort of operation can sort animals by name, breed, ID, and number age in both directions.

Algorithmic evaluation and outcomes

This work addresses the third course outcome, designing and evaluating solutions using algorithmic principles and explaining trade-offs. Building the two indexes takes O(n) expected time and O(n) additional space for n records. A repeated exact lookup avoids scanning all n records and takes O(1 + k) expected time before filtering and sorting k candidates, though broad rescue searches can still examine many records. Sorting m matches takes O(m log m). The earlier callback depended on another database query and result transfer for each selection, so its total latency cannot be fairly reduced to a single local complexity figure. The in-memory approach improves repeated interaction with a stable snapshot but requires a reload to reflect changes in MongoDB. It does not replace database indexes or pagination planned for the separate database enhancement. The fourth outcome is supported by integrating the new structure into the existing dashboard and keeping the CRUD module separate. My coverage plan remains focused on outcomes 3 and 4 for this enhancement; the written narrative also contributes to outcome 2.

Reflection

The first task to accomplish was to keep the initial rescue rules and implement the selection part via Python code. For every rescue category, I defined the list of breeds allowed, necessary sex and age of a candidate. Then I selected candidates based on indexed positions without duplicating the original records. I found out that an index is effective only with those access patterns it supports, thus, indexes by breed name and ID work directly, while a particular age range requires further comparison. Another important task was to maintain the separation of numeric ages sorting from text-based sorting and maintain predictability with empty values. Test queries using exemplary records confirmed working with overlapping rescue categories, applying multiple conditions, descending numeric sorting and non-matching searches. The current implementation can be tested locally, but a working MongoDB and Dash application is necessary for interface testing. The next step will be applying feedback from the instructor and testing the dashboard with the course database.

Artifact and origin

I selected the Grazioso Salvare Animal Shelter Dashboard that I created in CS 340 Client Server Development in 2026. The original Python notebook connects to MongoDB through an AnimalShelter CRUD module and displays Austin Animal Center records in a Dash table, breed chart, and map. Users select water, mountain, or disaster rescue criteria. This enhancement focuses on database access and follows my Module One plan for validation, controlled queries, indexes, pagination, aggregation, and error handling.

Why this artifact belongs in my ePortfolio

The project shows how stored data supports a practical application. I enhanced the CRUD layer so the dashboard passes controlled parameters rather than constructing database queries itself. The module validates allowed fields and values, rejects operator dictionaries, and builds the rescue conditions internally. I preserved the original breeds, sex requirements, and inclusive age ranges. Connection information now comes from environment variables, and database failures produce safe application messages instead of exposing raw driver errors. Writes require an animal ID filter, and new records require core identifying fields.

I added a compound index for rescue filtering and a nonunique animal ID index. The dashboard now retrieves ten records per page using database sorting and skip and limit operations. An internal MongoDB ID breaks sorting ties without being returned to the interface. The breed chart uses an aggregation pipeline to summarize all matching records instead of counting only the visible page. The map displays the selected record from the current page. The original code and enhanced implementation are included separately in the artifact ZIP.

Database evaluation and outcomes

This enhancement helped me work toward Outcomes 3, 4, and 5 from my Module One plan. For Outcome 3, I had to think about the benefits and limits of my database choices. Indexes can help MongoDB find matching records, but they also take up storage and add work when records change. Pagination keeps the dashboard from loading every result at once, although later pages can still take more work to retrieve. I would need to check a live MongoDB query plan before claiming a performance improvement. For Outcome 4, I used MongoDB indexes, aggregation, and a separate data-access layer to improve how the dashboard retrieves and summarizes records. For Outcome 5, I added validation, kept query construction inside the database module, moved connection information out of the source code, and made error messages safer. This narrative also supports Outcome 2 by explaining the changes and their purpose. I am still working toward the same outcomes I identified in my original plan.

Reflection

The main lesson was that scalability requires coordinated changes in the database and interface. Adding limit alone would leave the chart counting only one page. I addressed that problem by separating paginated records from the aggregation summary. I also kept the database enhancement separate from the in-memory AnimalIndex work completed for Milestone Three.

Another challenge was preserving the rescue rules while restricting inputs. Validation had to accept ordinary search values without allowing the interface to supply MongoDB operators. I also avoided treating animal IDs as unique because an animal can have multiple outcome records. Eight automated checks passed for pagination, rescue criteria, summaries, validation, CRUD safeguards, index setup, safe failures, and dashboard loading. An offline check with the supplied shelter dataset compared all rescue counts and summaries against independent Python calculations. These checks used a simulated MongoDB collection. Live authentication, query plans, performance, and browser interaction still need verification with the course database before final ePortfolio publication.
